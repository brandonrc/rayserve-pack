Proposed Ray Architecture — review from a working Tier‑3 deployment

These comments come from building and running the RayJob-per-execution design the proposal lists as “an optional future backend” (§12). Everything cited as evidence was measured on a live cluster running Keycloak, Envoy Gateway, nebari-operator, KubeRay and CheckMAITE, not inferred.

Reviewing rev c9044c211a88 Paste each block into its section’s annotation Evidence: rocky, 88 CPU / 156 GiB, CPU-only

Headline: the two designs are complementary, and the proposal’s central argument for Ray Client does not apply to one of CheckMAITE’s two clients.

§12 rejects Ray Jobs because it “would change the current interactive workflow and add startup and preparation time,” since users “would need to package and stage inputs rather than pass live objects.” That is correct for notebooks. It is not true of the web API: the CheckMAITE api never holds live Python objects — it holds catalog records with spec dicts and constructs the objects itself. For that client, declarative submission costs nothing and removes the version-parity coupling entirely.

Recommendation: adopt the proposal as written for notebooks, and RayJob CRs for UI/API submissions — one backend per client, selected by configuration. spec.clusterSelector lets those CR-tracked jobs run on the per-group clusters §5 already provisions, which removes the startup-time objection without a second cluster.

Comments by section

§4Shared model-servingagrees
“Users access only controlled inference endpoints, not direct Ray Client connections… dashboard API blocked from notebooks.”

This control now exists as deployable IaC and is worth adopting rather than re-specifying: the rayserve-pack hardening adds NetworkPolicy allow-listing (intra-Ray plus the KubeRay operator, then only explicitly listed client namespaces) and gateway-side claim authorization, defaulting to deny.

Verified under an enforcing CNI

unlisted pod  → head:8265   denied (connection timeout)
allow-listed namespace       → 200 {"ray_version": "2.43.0"}
non-member browser session   → 403 at the gateway, before the dashboard

One nuance for the doc: Ray’s dashboard REST API can submit and kill jobs, so “blocked from notebooks” has to mean network-level denial, not merely “not documented.”

§5Interactive environmentssizing gap
“1 head pod (1–2 CPUs, 4 GiB), 1 warm compute worker minimum (2 CPUs, 4–8 GiB)”

Both halves of that illustrative shape need revising for how CheckMAITE actually executes today.

The head carries the workload. A capability run executes in the job driver, which Ray places on the head — so torch, model weights and the dataset all live there. A MAITE evaluation with AlexNet was OOMKilled at 4 GiB. 8 GiB was sufficient.

Head OOM at the proposal’s illustrative size

1 worker(s) were killed due to the node running low on memory.
Memory on the node ... was 3.96GB / 4.00GB (0.990109)

The warm worker idles. One capability run is one Ray task — there is no fan-out per dataset or datum in 0.3.0. A dashboard sample of a shared cluster showed 16 tasks, all _execute_capability_ref. A minimum worker therefore holds a share of the group’s quota without receiving work; recommend making it opt-in per capability class.

§6Execution lifecyclerisk understated

The registry/controller pair does deliver the stated benefit — work survives notebook disconnection. The failure mode it does not survive deserves naming in this section, because the proposal makes Ray Client the primary path: a Ray Client session cannot be re-established after the head restarts, and CheckMAITE has no reconnect logic, so every subsequent submission from that process fails until an operator restarts it.

Observed after a head pod was recycled; persisted until the api restarted

client has already been disconnected due to an error. Last exception:
  status = StatusCode.NOT_FOUND
  details = "Attempted to reconnect a session that has already been cleaned up"

Suggested addition to this section: reconnect-on-dead-session is a requirement of the Ray Client path, not an optimization. Also worth verifying before sizing on it — the proposal states the registry reserves 0 Ray CPUs; in checkmaite 0.3.0 no explicit num_cpus is passed when the actor is created, so Ray’s actor default applies.

§8Isolation and authorizationagrees, extended
“A Ray namespace only organizes names and actors inside one Ray cluster; it does not enforce network access, permissions, or resource quotas.”

Independently confirmed, and the composite boundary this section defines — separate cluster, namespace, RBAC, NetworkPolicy, credentials, quota — is exactly what we deployed. Two additions from running it:

Separate entitlement from tenancy. “Which group’s namespace runs my work” and “may I run compute at all” are different questions and belong to different groups. With an entitlement group configured, a user holding a tenancy group but not the entitlement is refused before any record is created. 

carol  (cherry + ray-users)  → 202, job runs in cm-cherry
dave   (cherry, no ray-users) → 403 "membership of 'ray-users' is required to run jobs"

Name the default for unmapped callers. Our first implementation fell back to the api’s own namespace when a caller matched no group — which silently runs a stranger’s work in a namespace they have no claim to. Refusing is the correct default and worth stating here.

§9Scaling and schedulingagrees, one trap
“Kubernetes quotas limit the total size of each group cluster. Ray decides how tasks use that capacity internally.”

Confirmed, including scale-to-zero: with minReplicas: 0 a submission brought a worker up in ~15 s and the pod was released 120 s after the work finished.

The trap to document: ttlSecondsAfterFinished delays cluster teardown, and a finished-but-lingering cluster still holds the namespace’s quota. Three of them starved the next submission in testing. Size quota for max concurrency × cluster footprint across the TTL window, and note that RayService zero-downtime upgrades run the old and new cluster simultaneously — that path wants roughly 2× headroom.

§10Failure and upgradeadd three

Three startup failures that are invisible until you run this on a real cluster:

  • Probes assume wget. KubeRay’s default head and worker probes shell out to it; slim Python images (including CheckMAITE’s own api image, the natural job image) do not ship it, so pods never report Ready and the RayJob sits in Initializing until its deadline. A urllib check against the raylet health endpoint needs only the interpreter.
  • Login shells drop the venv. KubeRay starts Ray with bash -lc; /etc/profile resets PATH, so an image whose entrypoint relies on ENV PATH fails with ray: command not found. A /etc/profile.d snippet fixes it.
  • Ray sizes memory from the machine, not the cgroup. On an 88-core host, heads were OOMKilled until object-store-memory was capped and MALLOC_ARENA_MAX set. Anything sized per-container needs both.
§11Visibility and operationsmechanism matters
“CheckMAITE should present one execution ID and one coherent status. Ray actor, task, driver, pod, and node identifiers should remain available behind that execution for troubleshooting.”

Agreed as a goal, but the submission mechanism decides whether the second half is achievable. Over Ray Client, every run in a cluster appears as tasks beneath a single long-lived driver — there are no per-run entries in the dashboard’s Jobs view, which is exactly the confusion this section is trying to remove. With a RayJob per execution, each run is a first-class job with its own CR, submitter logs, and cluster, and the CheckMAITE execution ID maps one-to-one onto it.

Related operational note for this section: a per-job cluster’s dashboard exists only while the job runs, so “go look at Ray” is a narrow window. Two mitigations we use: raise the cluster TTL to keep a finished job browsable, and give each group a stable hostname whose Service selects whichever job cluster is currently live.

§12Ray Jobs as an alternativeprincipal comment
“an optional future backend… would change the current interactive workflow and add startup and preparation time”

Both objections are sound for notebooks and neither holds for the web API, which is where most submissions in a deployed product originate.

  • “Package and stage inputs” is already true there. The api builds models, datasets and metrics from catalog spec dicts; passing those specs to the job instead of constructing objects first is strictly less work, and it removes the requirement that api and every worker run an identical checkmaite build.
  • Startup time is optional. RayJob.spec.clusterSelector targets an existing cluster, so a CR-tracked job can run on the per-group cluster §5 provisions with no provisioning at all — the durable record, the namespace boundary and the absent Ray connection, at warm-cluster latency.

Both modes implemented and running

per-job cluster   : own environment, private failure domain, 25–60 s spin-up
clusterSelector   : runs on the group's existing cluster, no spin-up
selection         : per group, by configuration

Suggested rewrite of this section’s conclusion: Ray Jobs is not a future replacement for Ray Client but the appropriate backend for non-interactive clients, deployable alongside it today.

§13Tradeoffscosts to add

The cost list is candid; three more belong on it, all load-bearing:

  • Version parity is an operational coupling, not just a compatibility note. Because objects are cloudpickled by reference, any mismatch between the submitting environment and a worker is unrecoverable for in-flight work — and it constrains when either side may be upgraded.
  • The control plane is code someone maintains. The registry and controller actors, heartbeats, sweeps, retention and backpressure are roughly 1,800 lines of bespoke distributed-systems code in checkmaite. The CR-based adapter that replaces them for the UI path is roughly 400, because Kubernetes holds the state.
  • Storage must be reachable from every group namespace. A PVC in the api’s namespace is invisible to job pods in a group namespace — a run failed loading its dataset from a path that existed only inside the api. This makes an object store (or an RWX/ROX volume) a requirement of the group-isolation model, not an optimization.
§14Key decisionstwo to add

Suggest adding two decisions, both already implemented and running:

  • Submission backend is chosen per client. Notebooks keep Ray Client against the group’s persistent cluster; UI and API submissions create a RayJob in the caller’s group namespace. One deployment, two paths, no shared failure mode.
  • Entitlement is a separate group from tenancy. Membership of an entitlement group grants the right to run compute at all; tenancy groups decide whose namespace, quota and cluster run it. Adding a group is then a Keycloak group plus one values entry.

Six findings, with evidence

Consolidated for the record — each was reproduced on the cluster, and each one changes a number or a requirement somewhere in the proposal.

  1. Ray Client sessions are unrecoverable after a head restart

    Affects §6 and §10. Every submission fails until the api process restarts. The primary path in the proposal needs explicit reconnect handling.

  2. The job driver runs on the head, so the head needs the workload’s memory

    Affects §5. OOMKilled at 4 GiB running a MAITE evaluation; 8 GiB sufficient. The illustrative head size will not run that capability.

  3. A minimum warm worker receives no work today

    Affects §5 and §9. One capability run is one Ray task; the reserved worker holds quota without executing anything.

  4. Finished clusters keep holding quota for their TTL

    Affects §9. Three lingering clusters blocked the next submission. Quota must cover concurrency × footprint across the TTL window.

  5. Slim images break KubeRay’s defaults in two places

    Affects §10. Probes need wget; login shells reset PATH. Both leave a cluster stuck in Initializing with no obvious cause.

  6. Group isolation forces the storage decision

    Affects §8 and §13. Job pods cannot mount the api namespace’s PVC, so shared object storage is a precondition of per-group execution.

Available to adopt

All of the above is running, with tests, and can be handed over rather than rebuilt: the RayJob backend and its group routing, entitlement and scoping policy (checkmaite-frontend, 139 tests); batch runs scoped to the submitter’s groups; identity read from the gateway-verified ID token; the NetworkPolicy/quota/authorization hardening §4 and §8 call for; and a chart that provisions a group’s namespace, quota, RBAC, hostname and dashboard from a single values entry.
